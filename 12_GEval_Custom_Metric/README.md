# G-Eval Custom Correctness Metric

This practical example demonstrates how to create a custom correctness metric using DeepEval’s `GEval`.

The project evaluates live responses generated by an AI event-ticket support assistant against business rules, expected outputs and custom evaluation steps.

## What is G-Eval?

G-Eval is an LLM-as-a-judge framework that allows us to create custom evaluation metrics using natural-language instructions.

In this example, we define how the judge should evaluate:

- Refund eligibility
- Ticket-transfer eligibility
- Mandatory process information
- Unsupported promises or exceptions
- Overall policy correctness and completeness

G-Eval then returns:

- A score between 0 and 1
- A pass/fail result
- A reason explaining the score

## Evaluation workflow

```text
Event-ticket policy
        ↓
Customer question
        ↓
Application LLM generates a live response
        ↓
G-Eval receives:
- Customer input
- Actual AI output
- Expected output
- Policy context
- Custom evaluation steps
        ↓
Score + reason + PASS/FAIL
```

## Business policy

The example policy includes rules for:

- General Admission refunds
- Non-refundable VIP tickets
- Ticket transfers
- Seven-day refund limits
- Twenty-four-hour transfer limits
- Non-refundable booking and processing fees
- Refund processing time
- Customer identity verification
- Unsupported policy exceptions

## Test scenarios

| Test ID | Scenario | Risk being tested |
|---|---|---|
| TC01 | VIP refund and eligible transfer | Incorrect refund or missing transfer requirements |
| TC02 | Eligible General Admission refund | Missing fees, timeline or verification |
| TC03 | Transfer requested inside 24 hours | Incorrectly allowing a prohibited transfer |

## Custom evaluation logic

The G-Eval metric checks whether the response:

1. Identifies the relevant ticket type, action and time remaining.
2. Makes the correct refund or transfer decision.
3. Includes mandatory information relevant to the question.
4. Avoids irrelevant policy details.
5. Avoids unsupported promises or exceptions.
6. Correctly prioritises serious business-rule violations.

An incorrect refund or transfer decision is heavily penalised. Missing mandatory process information is moderately penalised.

## Results

| Test | Score | Threshold | Result | Finding |
|---|---:|---:|---|---|
| TC01 | 0.62 | 0.80 | FAIL | Identity-verification requirements were missing |
| TC02 | 0.62 | 0.80 | FAIL | Non-refundable fees and refund timeline were missing |
| TC03 | 0.93 | 0.80 | PASS | Transfer was correctly rejected inside 24 hours |

## Key findings

TC01 and TC02 provided the correct primary answer but omitted mandatory business information.

A traditional keyword check might have passed these responses because they contained the correct refund or transfer decision. The custom G-Eval metric assessed both correctness and completeness and detected the missing requirements.

TC03 correctly rejected the transfer request because only 12 hours remained before the event.

## Important QA observation

The judge’s TC03 explanation stated that the response identified the ticket type, although the customer did not provide a ticket type.

This did not change the correct verdict, but it demonstrates why QA engineers should inspect the judge’s explanation instead of trusting only its numerical score.

## Why use expected output and policy context?

The expected output describes the correct behaviour for the specific test scenario.

The policy context provides the complete source of truth.

Supplying both helps the evaluator compare the response against:

- The expected scenario outcome
- The underlying business rules

## Run the example

Activate the repository-level virtual environment:

```bash
source ../.venv/bin/activate
```

Run the evaluation:

```bash
python test_event_ticket_ai.py
```

The program will:

1. Generate three live responses.
2. Evaluate each response using the custom G-Eval metric.
3. Display the score, threshold, verdict and reason.
4. Save all results to `correctness_results.json`.

## Environment variable

Create a `.env` file in the repository root:

```text
OPENAI_API_KEY=your_api_key
```

Never commit the `.env` file or API key.

## Key lesson

A response can make the correct main decision and still fail because it omits mandatory business information.

G-Eval allows QA engineers to define custom semantic evaluation rules, but the judge is also an AI system. Its scores and explanations must be calibrated, reviewed and supported by deterministic checks for critical requirements.
